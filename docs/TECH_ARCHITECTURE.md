# 技术架构

## 阶段一选型

**原生 HTML + CSS + JavaScript ES Modules，SVG/CSS 角色与场景视觉。**

目前产品风险在于陪伴体验、关系状态和碎片化对话是否成立，而非大规模实时渲染。因此先用浏览器技术降低 Windows 开发门槛、支持窄屏和 AI 协作。运行不依赖包管理器或外部库，代码可由静态服务器直接提供。

Godot 4 适合后来需要场景编辑器、骨骼动作、引擎工具链和原生包体时重新评估。Three.js 适合在既有 Web UI 中逐步替换角色舞台，并沿用浏览器渠道。是否迁移由性能、角色表达和打包需求共同决定；现在不强行预判最终引擎。

## 模块边界

- data/：角色定义、对话、短信和剧情场景数据。用稳定 ID 关联存档，不以角色数量分支硬编码。
- src/core/affection.js：好感增减与等级判断。
- src/core/game-state.js：按角色保存关系、消息、选择和剧情旗标；提供事件方法。
- src/core/save.js：浏览器本地存档读写与异常回退。
- src/ui/character-stage.js：角色展示适配器。当前加载 SVG 并呈现表情、动作与交互热点；未来可以替换 Three.js 实现。
- src/ui/*-view.js：独立页面视图，接收角色和状态数据。
- src/app/main.js：导航和用户事件编排，不承载角色文本与故事内容。

## 状态流向

UI 用户操作 → 核心状态动作 → 按 male_01 更新本机存档 → 订阅更新 → 重绘当前视图。故事完成用旗标触发条件台词，并将后续消息写进同一角色收件箱。引入第二角色时为 male_02 添加配置即可使用相同状态 API；后续关系 schema 的版本迁移会随存档升级再加入。

## 后续能力边界

当前用 CharacterStage 作为 2D/3D 交界。消息服务、云端账号、AI 动态对话、电话、语音、换装、卡牌、抽卡与战斗均未实现，不伪装成已连接能力。建议按以下触发条件再引入：

- Three.js/Unity/Godot 实时角色：已有明确表情、动作、光照和性能需求。
- PWA/移动端壳：已有持续使用需求与离线资源清单。
- 云端服务：跨设备同步或主动推送成为核心价值，并明确隐私与成本模型。

## 运行与调试

在 Windows PowerShell 中运行根目录的 run-local.ps1，再用浏览器打开脚本显示的本机地址。数据与文案使用原生模块，避免 file:// 的 ES Module 跨域限制。该服务器只绑定 127.0.0.1。浏览器存档键为 fog-harbor-save-v1。
